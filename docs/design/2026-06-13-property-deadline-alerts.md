# Design: In-App Property Deadline Alerts (and closing the AI capability-honesty gap)

## Problem Statement

The conversational assistant offered to "set up tracking" for a property. When the
user accepted ("Yes please set up"), the model admitted it has no tracker tool and
fell back to "Manual Tracking Tips." (Reproduced from a production screenshot,
vercel `*-alpha` deployment.)

Two distinct problems are tangled in that one screenshot:

1. **A missing capability.** Users want to be notified when something changes on a
   property they care about. The product cannot do this today.
2. **A capability-honesty bug.** The assistant proposes actions ("set up tracking,"
   "set up monitoring") that map to no callable tool, so it promises things it
   cannot do and then has to walk them back. This erodes trust on every turn, not
   just for tracking.

The narrowest, highest-confidence wedge that addresses both: **in-app alerts for
auction deadlines on saved properties**, plus a real agent tool so the assistant
only ever offers what it can actually do.

## Demand Evidence

- Direct, observed production behavior: a real user explicitly asked the assistant
  to "set up" tracking/monitoring for a Chennai flat and was turned away. That is a
  user reaching for a capability mid-conversation, not a survey response.
- The product already ships a watchlist (`User -[:SAVED]-> AuctionProperty`); the
  screenshot shows a heart/favorites badge of 3. Users are already curating a set of
  properties they care about, which is exactly the population that wants deadline
  alerts.
- Caveat (honest): this is one observed interaction. It is strong signal of intent
  but not yet evidence of repeated demand. The assignment below is designed to widen
  that evidence.

## Status Quo

Today a user who wants to "keep an eye on" a property has no in-product mechanism.
Their workaround, as the assistant itself suggested, is manual: bookmark the source
listing (e.g. the Arcil page), and re-check it by hand. For time-boxed SARFAESI
auctions, the failure mode is concrete and painful: the bid deadline passes while
the property sits unattended in a bookmark folder. The cost is a missed auction.

## Target User & Narrowest Wedge

**Target user:** an active auction investor using the app, who has saved a handful
of Tamil Nadu SARFAESI properties and needs to act before each one's bid deadline.

**Narrowest wedge (what we build now):** for each of the user's `:SAVED`
properties, surface an in-app alert when its auction deadline falls inside a
threshold window (7 / 3 / 1 days out). A bell icon with an active-alert-count badge
opens a feed of these alerts. No email, no SMS, no new scraping, and — see the
roadmap note — no re-auction alerts yet (they require persistence and belong in
phase B). The assistant gets `watch_property` and `list_alerts` tools so "yes please
set up" calls a real function and reports a real result.

## Constraints

- **No production scraper/scheduler.** Scrapers are Selenium-based, run locally and
  in batch (`pipeline/config.py`, `pipeline/run_pipeline.py`). There is no live
  re-fetch loop. Therefore the first version must use signals computable from data
  already in Neo4j (auction dates, re-auction edges) — no price/status diffing,
  which would require re-scraping.
- **Auth + data already exist.** Supabase JWT auth mirrored to `:User` nodes;
  watchlist via `api/watchlist`. We reuse both rather than add new identity or
  storage concepts.
- **DeepSeek V4 Pro via OpenRouter, PydanticAI agent.** New tools follow the
  existing `@agent.tool_plain` pattern in `api/agent.py` (11 tools today, e.g.
  `search_auctions`, `semantic_search`, `select_properties`).
- **Web feature on existing deploy pipeline** (Vercel frontend + Render backend).
  No new distribution artifact.

## Premises

All five confirmed by the user during the session:

1. The real bug is capability/promise mismatch, not just a missing feature. The fix
   is feature + a real agent tool + system-prompt grounding, so the assistant stops
   offering tool-less actions.
2. Alerts key off the existing watchlist (`:SAVED`). Saving a property opts it into
   deadline alerts; no separate "watch" concept is introduced.
3. Deadline alerts need no scheduler if computed on-read. The signal is purely
   `auction_date − now` against thresholds, computable lazily when the alerts
   endpoint is hit. A cron job is only required for persistent read/unread state and
   dedupe (deferred to phase 2).
4. No new distribution channel — this ships through the existing web deploy.
5. The assistant gets `watch_property` / `list_alerts` tools so accepting a
   suggestion invokes a real function instead of falling back to manual tips.

## Approaches Considered

### Approach A: Lazy on-read compute (CHOSEN for now)
- **Summary:** A `GET /alerts` endpoint computes, per request, which of the user's
  `:SAVED` properties have an auction deadline inside the 7/3/1-day thresholds,
  straight from Neo4j. A bell + feed renders it; badge = active-alert count. Agent
  gains `watch_property(auction_id)` (idempotent watchlist add, via the existing
  watchlist write repo) and `list_alerts()` (same compute). System prompt grounded
  so accepting a suggestion calls a real tool. (Re-auction alerts are deferred to B
  — without persistence there is no way to tell a "new" re-auction link from an old
  one, so they cannot be made correct here.)
- **Effort:** S · **Risk:** Low
- **Pros:** No scheduler, no new node type, no migration; one PR. Still fixes the
  AI-honesty bug because the tool + grounding are in scope. Endpoint/tool shapes are
  designed to grow into B.
- **Cons:** No read/unread or "new since last visit"; recomputed every load; no
  alert history.
- **Reuses:** `api/watchlist` repo, `@agent.tool_plain` pattern, existing
  `auction_date` / re-auction fields in the graph.

### Approach B: Persisted notifications + daily cron (phase-2 roadmap)
- **Summary:** Introduce `Notification` records (Neo4j node or table) with
  type/created/read state. A Render cron (slot already exists in `render.yaml`)
  scans saved properties daily and writes one deduped alert row per threshold
  crossing. Endpoints for list / mark-read / unread-count. Same agent tools +
  grounding.
- **Effort:** M · **Risk:** Med
- **Pros:** Real notification semantics (unread badge, history, "new since last
  visit"). This is the platform that phase-2 price/status alerts plug into — add new
  producers to the same cron + model.
- **Cons:** Cron to operate, dedupe correctness, a new node type to migrate and
  maintain.

### Approach C: Capability registry, alerts as entry #1 (roadmap / root-cause)
- **Summary:** A thin single source of truth for what the assistant can actually do,
  injected into the system prompt and backing the tools, so the model structurally
  cannot offer a tool-less capability. Alerts is the first entry; chat and bell feed
  render the same tool output, guaranteed consistent.
- **Effort:** M · **Risk:** Med
- **Pros:** Fixes the reported class of bug (AI promising vapor) for all future
  capabilities, not just tracking.
- **Cons:** Registry abstraction is premature for a single capability; pays off only
  once several capabilities exist.

## Recommended Approach

**Build A now; record B and C as the sequenced roadmap** (the user's explicit
choice).

Rationale: A delivers exactly the wedge the user chose (deadline-only, in-app-only)
with the least infrastructure, while still including the agent tool and prompt
grounding — so it genuinely stops the assistant from promising what it can't do. B
is the correct next step the moment price/status diffing is on the table, and A's
endpoint and tool shapes are deliberately designed to grow into B's persistence
model without a rewrite. C is the elegant end-state for capability honesty but is
not justified by a single capability yet; it becomes worthwhile once there are
several tool-backed suggestions to guard.

### Implementation sketch for A (for the downstream eng-review)
- **Backend (`api/`):**
  - New `api/alerts/` module: `compute_alerts(user_id)` reads `:SAVED` auctions for
    the user, computes `days_to_deadline = auction_date − now`, and emits exactly one
    alert per property: severity = the smallest threshold the property satisfies
    (≤1 → "urgent", else ≤3 → "soon", else ≤7 → "upcoming"); properties with
    `days_to_deadline > 7` produce no alert. Returns typed alerts (auction_id,
    severity, days_left, message, deep-link). Properties with a null, missing, or
    unparseable `auction_date`, or whose deadline has already passed, are excluded.
  - `/alerts` router returning the computed list + count. For authed users, `GET
    /alerts` resolves the saved set server-side from their `:User` node. For
    anonymous users the client sends its localStorage watchlist `auction_id`s — since
    a GET can't carry a body, use `POST /alerts` with the IDs in the body (mirroring
    how the existing `/watchlist` endpoint accepts client-side IDs); the endpoint
    computes alerts over that set. (Pick one verb convention with the existing
    watchlist endpoints during eng-review.)
  - Reuse `api/watchlist/repository.py` for the saved-set read. `watch_property`
    calls the existing watchlist write path; no new write path is introduced.
- **Agent (`api/agent.py`):**
  - `@agent.tool_plain watch_property(auction_id)` → idempotent watchlist add (so
    "yes please set up" works even if the property isn't saved yet), returns a
    confirmation + the alerts now active for it.
  - `@agent.tool_plain list_alerts(auction_id?)` → wraps `compute_alerts`, optionally
    filtered to one property.
  - Grounding: update `_ROLE_PROMPT` (`api/agent.py:49-85`) and
    `modes/_shared.md` so the assistant (a) knows these tools exist, (b) offers
    "tracking/monitoring" only as deadline alerts via these tools, and (c) never
    invents a capability that has no tool. Keep the existing "confirm before
    state-changing action" rule for `watch_property`.
- **Frontend (`web/`):**
  - Bell icon in the bottom nav (next to the heart in the screenshot) with a badge =
    active-alert count; tapping opens a feed listing alerts. Each alert deep-links to
    the existing property detail route (the same target `select_properties` / the
    matches panel already opens — confirm the exact path in `web/` during eng-review).
  - Empty state ("No deadlines coming up on your saved properties") and the urgent
    state ("Bid closes in 1 day").
- **Tests:** unit tests for threshold bucketing (boundary cases: exactly 7/3/1 days,
  already-passed deadline excluded, timezone handling for auction dates), agent-tool
  registration tests mirroring the existing router/tool tests, and an endpoint test
  for the authed + anonymous paths.

## Open Questions

- **Timezone of `auction_date`.** Thresholds must be computed in IST (auctions are
  Tamil Nadu / SARFAESI). Confirm how `auction_date` is stored in Neo4j (UTC vs.
  local) before computing `days_to_deadline`. This is the most likely correctness
  bug.
- **Passed deadlines.** Should an alert for an already-passed deadline disappear
  silently, or show a one-time "this auction has closed" state? Recommend silent
  removal in A; revisit with persistence in B.
- **Anonymous users.** Watchlist supports anonymous (localStorage-synced) users.
  Confirm alerts should work for them too (recommend yes, for parity).
- **Badge semantics without persistence.** In A the badge is "active alerts now,"
  not "unread." Acceptable for the wedge; B upgrades it to true unread.
- **Re-auction freshness moved to B.** A re-auction alert needs to distinguish a
  newly-linked `:SAME_PROPERTY_AS` edge from an old one, which requires stored state.
  Deferred to B with the rest of the persistence work.

## Success Criteria

- Replaying the screenshot flow, the assistant calls `watch_property` (and reports a
  real confirmation) instead of falling back to "Manual Tracking Tips."
- A user with a saved property whose deadline is ≤7 days out sees a bell badge and a
  correct alert in the feed, with a working deep-link to the property.
- Threshold bucketing is correct at the 7/3/1-day boundaries and in IST; passed
  deadlines and properties with null/unparseable `auction_date` never show as
  upcoming.
- Capability-honesty check: the grounded system prompt is audited against the actual
  registered tool list, and the assistant offers "tracking/monitoring" only as
  deadline alerts via `watch_property` / `list_alerts` — no other tool-less action is
  proposed in a replay of common "set up / monitor" phrasings.
- No new scheduled job, node type, or migration is introduced (A stays within its
  scoped footprint).

## Dependencies

- Read access to `auction_date` on saved `AuctionProperty` nodes in Neo4j (already
  present). (`:SAME_PROPERTY_AS` re-auction edges are only needed once re-auction
  alerts land in phase B.)
- `api/watchlist` repository (exists).
- Frontend nav has room for a bell entry (the screenshot's bottom nav already hosts
  home / chat / favorites).

## What I noticed about how you think

- You framed this as "interesting that AI has suggested something but we didn't had
  capability" — you led with the *mismatch*, not the missing feature. That instinct
  (the bug is the broken promise, not just the absent button) is why premise #1
  landed without pushback; most people would have just said "add a tracker."
- When the wedge question offered richer "price/status changed" alerts, you chose
  "deadline/date alerts only (free signals)." Picking the version that can't be
  wrong over the version that's more impressive is a taste call, and the right one
  for a trust-repair feature.
- "A now, write B + C as roadmap" — you didn't discard the bigger ideas, you put
  them on the record and shipped the small one. That's the narrowest-wedge pattern
  done deliberately, not by accident.
